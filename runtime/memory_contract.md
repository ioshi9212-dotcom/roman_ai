# MEMORY CONTRACT

Не смешивай пять разных вещей.

## CARD
Кто персонаж вообще: личность, характер, биография, прошлое, привычки, устойчивые цели и важные связи. Полные карточки живут в `characters.json`. Они не переписываются каждый ход.

Card — объективное авторское знание. Факт из Card не становится знанием другого персонажа автоматически.

Если во время игры появляется новый recurring/important NPC, сохрани его через `character_upserts`. Одноразовый фоновый человек карточки не требует.

## STATE
Что с персонажем сейчас: место, присутствие в сцене, физическое состояние, текущая цель/статус, предметы и другое временное состояние. Это `state.json`.

## RELATIONSHIPS
Направленное устойчивое отношение конкретного NPC к POV. Хранится постоянно в `state.json -> relationships` и не исчезает, когда NPC уходит из сцены.

Основная рабочая связь: только `NPC -> POV`. Она влияет на поведение NPC вместе с Card, PERSONAL MEMORY, целями, обязанностями и текущим состоянием.

Отношения не являются памятью и не являются знанием. Сила отношения не даёт NPC факты, которых он не воспринимал и не получал.

Видимый footer сцены показывает только отношения присутствующих NPC -> POV. POV -> NPC не назначать. NPC -> NPC в footer не показывать.

## CHRONOLOGY
Что объективно произошло в мире и должно остаться важным через много ходов.

Chronology нужна автору для непрерывности. Она не является памятью персонажей и не сообщает, кто знает записанный факт.

Chronology должна быть плотной, а не стенограммой жизни. Обычно `0–2` записи на ход. Несколько связанных действий одной сцены объединяются в одну запись.

Сохранять только устойчивые сюжетно важные события, знания, решения, изменения, последствия и связи, без которых будущее станет непонятным.

Не сохранять отдельно бытовую рутину и внутренние мысли без значимого последствия.

Текст события обычно 1–3 плотных предложения. Не пересказывать сцену целиком.

Дата хранится, если известна. Время по умолчанию хранится широким периодом. Точное время сохраняется только при `time_critical=true`, когда часы важны для причинности.

`importance=anchor` использовать для долговечных опорных событий, которые должны возвращаться в long-range chronology спустя много ходов.

Даже если событие есть в chronology, персонаж может использовать его только если лично воспринял, получил или уже хранит соответствующее знание в PERSONAL MEMORY.

## PERSONAL MEMORY
Для каждого персонажа отдельно.

### knowledge
Что именно этот персонаж знает или считает правдой.
Поля по возможности: `fact_id`, `content`, `source`, `learned_turn`, `confidence`.

### experiences
Что именно этот персонаж лично видел, слышал, сделал, получил или пережил.
Поля: `event_id`, `turn`, `summary`, `role`.

### dialogue_memory
Важные темы разговоров, в которых именно этот персонаж участвовал или которые лично слышал.
Поля: `topic_id`, `turn`, `asked_by`, `asked_to`, `question`, `answer`, `status`.

ID для новых knowledge/experience/dialogue записей может быть добавлен сервером автоматически, если модель его не указала. Нельзя терять запись только из-за отсутствующего ID.

## КТО ЧТО ВИДЕЛ И СЛЫШАЛ
На каждом ходу проверяй персонажей сцены по отдельности.

Для каждого персонажа:
1. был ли он физически присутствующим в момент события;
2. мог ли он это увидеть или услышать;
3. получил ли он информацию прямым способом;
4. только после этого сохраняй новые knowledge, experiences или dialogue memory именно ему.

Персонаж, которого не было рядом, ничего не узнаёт автоматически.
Персонаж, пришедший позже, не знает прошлую часть сцены без отдельного источника.
Персонаж, ушедший раньше, не знает последующие события.
Chronology не раздаёт знания персонажам автоматически.

### ПРИВАТНЫЕ КАНАЛЫ POV
Приватный контент POV по умолчанию доступен только POV.

Присутствие рядом не означает доступ к содержимому. NPC узнаёт его только через реально установленный канал передачи или восприятия.

Если NPC находится в другом месте, ушёл раньше или пришёл позже, нужен отдельный источник передачи.

### НЕ ЛЕГАЛИЗОВАТЬ УТЕЧКУ
Если NPC случайно использовал факт, которого не мог знать, сцену нужно переписать до `commitTurn`.

Ошибочная утечка не создаёт новое законное знание, не становится каноном и не сохраняется в personal memory.

Авторское объяснение не является источником знания. Вывод допустим только из конкретных предпосылок, доступных самому NPC.

## ОБЯЗАТЕЛЬНЫЙ PERSISTENCE REVIEW
После каждой сцены перед `commitTurn` нельзя отправлять пустой `extracted`.

Всегда передать:
- `persistence_reviewed=true`;
- `chronology`;
- `knowledge_add`;
- `experiences_add`;
- `dialogue_memory_add`.

Пустые списки допустимы только после реальной проверки.

Для knowledge/experience/dialogue не обязательно придумывать ID вручную: сервер добавит устойчивый ID, если он отсутствует.

## ПРАВИЛА
- У каждого персонажа своя память. Не копируй знание между персонажами без источника.
- Перед каждой репликой, вопросом, догадкой, узнаванием или осознанным действием NPC проверяй его personal memory и доступное восприятие текущей сцены.
- Перед каждой значимой реакцией NPC на POV проверяй его сохранённый `relationship_to_pov`.
- `chronology`, `recent_turns`, Card, hidden lore, source canon и чужая memory не являются источниками персонального знания.
- Приватное содержимое POV не становится знанием NPC без установленного канала передачи или восприятия.
- Ошибочно сгенерированная утечка знания не становится памятью.
- Ложь хранится как полученная информация, а не автоматически как мировая истина.
- Лично пережитое не исчезает только потому, что прошло много ходов.
- Отношение NPC к POV не исчезает только потому, что персонаж сейчас отсутствует.
- Отношение отсутствующего NPC меняется только если он реально получил информацию или пережил событие, способное на него повлиять.
- Уже отвеченный вопрос не повторяется случайно. Повтор требует причинного основания.
- Старую память не удаляй из-за временной нерелевантности.
- Card задаёт личность и прошлое; memory даёт доступные знания и опыт; relationships задаёт отношение NPC к POV; state показывает настоящее; chronology хранит объективную историю для автора.
