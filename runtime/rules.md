# RUNTIME RULES

Backend хранит канон и состояние.

## Файлы сессии по шаблонам генератора

В `state/` ровно десять JSON-шаблонов для постоянного хранения сессии: `state.json`, `анкета.json`, `карточка_персонажа.json`, `локации.json`, `отношения.json`, `память_персонажа.json`, `персонажи.json`, `сессия.json`, `скрытый_лор_и_крючки.json`, `хронология.json`. Рабочие карточки лежат в `карточки/<id>.json`, личная память — в `память/<id>.json`; для POV создаются оба файла. Общие файлы — по именам шаблонов. Числовая обработка отношений остаётся по механике Roman AI ниже; памятки в шаблонах не добавляют новых обязательных Actions или проверок.

Каждый `prepareTurn` нового формата читает **полную** `хронология.json` в `chronology.дни` и **полные** `память/<id>.json` участников в `character_memory[id].знания` и `личные_события`. Это не последние N записей и не выборка по ключевым словам. Дата группирует реальные сведения; источник сообщения сохраняется в самой фразе. «Со слов персонажа» не превращается в объективную истину. Память отсутствующих догружай перед их участием через обычный character bundle.

Хронология доступна только режиссёру. Ни запись здесь, ни реестр, ни чужая карточка или память не дают знания POV/NPC. У каждого участника собственное восприятие и память. Отсутствующий файл хронологии или памяти участника останавливает подготовку; не объявляй пустую память прочитанной и не придумывай её содержимое.

Существующие V5-сессии переносятся на эти файлы с тем же ID, архивом и личными знаниями. Прежние имена `memory.json`, `chronology.json`, `characters.json`, `relationships.json`, `meta.json` допустимы только как внутренние совместимые представления API, не вторые сохранённые файлы. Сохранение по-прежнему через один `commitTurn` и существующие `extracted` поля. Технические `_runtime`-метаданные не являются личным знанием и не поступают в игровой контекст.

Skin Builder определяет поведение POV, NPC, мира, построение сцены и формат ответа.

Rules выполняет только техническую работу:
- что прочитать;
- откуда брать данные;
- какие данные director-only;
- кого и когда догрузить;
- что и куда сохранить;
- как обновить state, chronology, knowledge, relations, intents, threads и presence;
- как выполнить commit и audit.

Не задавай через Rules поведение персонажей, режиссуру, темп, жанровую подачу или конец сцены. Это делает Skin Builder.

## НАСТРОЙКА ДО ПЕРВОГО ХОДА

Новые черновики создаются через `createNovelDraft` с `version=5` (это и серверное значение по умолчанию). Версии 1–4 сохранены только для совместимости существующих данных. В V5 нет обязательных `foundation`, fact_id/source_unit_id или стартовой сверки отношений с цитатами.

Десять файлов `state/` — схема хранения сессии, а не десять разделов для ручной отправки. Сервер создаёт реестр, хронологию, отношения, state и персональные файлы. `profile_schema.setup_sections` перечисляет входные разделы API:

- `novel`: объект анкеты; `pov_id` / `pov_character` указывает постоянный ID POV;
- `characters`: массив персональных карточек; ID и имя обязательны, POV можно дополнительно отметить `is_pov=true`;
- `locations`: массив профилей важных мест;
- `hidden_lore`: объект `{"entries":["текст"]}`;
- `knowledge`: объект `{"character_id":["стартовый личный факт"]}`;
- `canon_notes`: массив объектов `note_id`, `text`, `subjects`;
- `lore`: объект открытого лора.

Обязательны содержательные `novel`, `characters` и дословный проверенный RAW `intake`. Остальные разделы заполняются по наличию данных. `_памятка` и `_формат_*` — метаданные шаблонов, не канон. Не отправляй их как сведения истории.

1. Сохрани весь RAW через `appendDraftIntakeChunk(full_raw=true, chunk_index=0)`. Проверь `complete`, `char_count`, `raw_sha256`. При загрузке частями сохраняй точный порядок, тот же block_id/stage и `is_last=true` только в конце.
2. Сохрани профили через `saveNovelDraftSection`. В КАЖДОЙ записи передавай `expected_revision` из последнего ответа `revision` или `draft_revision`. Сохранения последовательны; RAW и mapping тоже могут увеличить revision. При конфликте прочитай текущий черновик, не повторяй старую revision вслепую.

**Дословность авторского канона:** каждый перенесённый из TXT текстовый фрагмент сохраняй без смягчения, сокращения, замены лексики или изменения пробелов. В `saveNovelDraftSection` передавай `source_quotes`: JSON Pointer (например `/0/character` для массива персонажей) → точная цитата из RAW, полностью совпадающая со значением поля. Сервер проверяет источник и защищает цитату при следующих правках. Новые придуманные GPT подробности допустимы только в отдельных `generated_details` и не являются авторским каноном. Пустой `source_quotes` НЕ подтверждает, что все поля переписаны без ошибок; нужна самостоятельная сверка с RAW.
3. Отметь каждый RAW-блок через `updateDraftIntakeMapping(fact_ids=[], reviewed_against_raw=true, expected_revision=...)` после переноса его содержания в профили.

**Проверка утраты авторских формулировок:** ответ статуса черновика V5 содержит `literal_raw_coverage`. Если `literal_lines_not_found > 0`, проверь указанные `block_id/line` по исходному RAW и перенеси важные авторские фразы дословно, отдельно от `generated_details`. Это диагностический список: он НЕ доказывает полноту смыслового переноса и не является разрешением выдумывать пропущенные знания. Префикс из старой неудачной загрузки не должен учитываться дважды, если имеется полный RAW.
4. `prepareDraftRead` → каждый `getNovelReadChunk`, включая индекс 0. Для той же revision продолжай тот же read_id с next_chunk_index. Реальное исправление профиля требует нового полного чтения; идентичная повторная запись не меняет revision.
5. `confirmDraftReconciliation(expected_revision=..., confirmed_against_raw=true, unresolved_conflicts=[])` → `finalizeNovelDraft`.
6. При запуске: `setDraftLaunchState(expected_finalized_revision=..., starting_state_json=...)` → `createSessionFromDraft`. Запуск использует отдельный физический state; содержательная анкета не требует state заранее. Повтор создания для той же finalized revision и launch state возвращает прежний session_id.
7. Первый `prepareTurn(opening_scene=true,user_input="",request_id=...)` и `commitTurn(user_input="")`.

Подтверждение читателя завершает ввод; проверки чтения и reconciliation выполняет ассистент. Они не требуют повторного пользовательского «подтверждаю». Неразрешимый смысловой конфликт уточняется отдельно.

## ПОРЯДОК ХОДА

Каждый ход:

1. `prepareTurn`.
2. Прочитай packet целиком.
3. Проверь state, continuity, active intents, threads и весь cast registry.
4. Если зарегистрированный offscreen NPC должен реально войти в текущую сцену или начать remote-участие - до его участия загрузи его полный character bundle.
5. Подготовь `scene_output` по `scene_builder`.
6. Только после готовой сцены определи реальные изменения.
7. Подготовь persistence/update данные из реально произошедшего.
8. Выполни проверки.
9. Один `commitTurn`.
10. Сцену показывай после успешного commit.

Не записывай будущий результат заранее и потом не подгоняй сцену под уже подготовленный state.

Основная сцена определяет, что реально произошло в текущем ходу.

## PREPARE TURN

`prepareTurn` packet - основной набор данных текущего хода.

Прочитай packet целиком.

Packet может содержать:
- user_input / `ordered_segments`;
- текущий state;
- physical и remote участников;
- их factual knowledge;
- profiles;
- relationships;
- active intents;
- threads;
- continuity;
- chronology;
- location context;
- director-only данные;
- другие данные текущей сцены.

`player_input_map.ordered_segments` — точный последовательный разбор ввода: `spoken` и `stage_direction`. Это транспортное представление; применение ввода к сцене определяет `scene_builder`.

`запускай первую сцену` на turn 0 - служебная команда, а не реплика POV.

## OPENING SCENE

Если `opening_scene.active=true` или turn 0 запущен служебной командой начала сцены, пользователь ещё ничего не сказал и не сделал.

Стартовые данные берутся из `novel.start`, `starting_state`, даты, времени, места и списка участников. `opening_scene=true` передаёт пустой `user_input` в prepare и commit.

Не превращай служебную команду в текст POV.

## CHARACTER BUNDLE

Для physical/remote участников packet уже может содержать их полный factual knowledge journal, собственный profile, relationships, perception/state и intents.

Если зарегистрированный offscreen-персонаж начинает реально участвовать в сцене, до его первой значимой реплики или действия выполни:

`prepareCharacterBundleRead`

затем прочитай все:

`getCharacterBundleChunk`

Bundle должен быть дочитан полностью до использования персонажа.

Offscreen упоминание само по себе не требует bundle.

Если NPC только упомянут, но не входит в сцену и не участвует удалённо - не загружай его карточку без необходимости.

## DIRECTOR-ONLY ДАННЫЕ

Не являются личным знанием персонажей:

- чужие profiles;
- чужие knowledge journals;
- chronology/history;
- hidden_lore;
- foundation;
- future_guidance;
- active_threads;
- story direction;
- `cast_index`;
- полный scene_state;
- чужие npc_active_intents;
- `canon_notes_context`, если персонаж не получил эти сведения внутри истории.

`foundation` и `future_guidance` - материал истории, а не уже произошедшие события.

Chronology - объективная история для режиссуры, а не автоматическая память персонажей.

## KNOWLEDGE

У каждого персонажа свой factual knowledge.

Персонаж получает только реально доступную ему информацию.

Не записывай в knowledge:
- director-only данные;
- чужую память;
- скрытые мысли POV;
- недоступную часть scene_state;
- вероятное заполнение неизвестной детали.

Частичный факт остаётся частичным.

Если известно только:
`свидание в субботу`

это не даёт автоматически:
- время;
- место;
- партнёра.

Не достраивай неизвестные поля вероятными значениями.

Сообщённая персонажем информация сохраняется как сообщённая информация, а не автоматически как объективная истина.

Например:

`Елена сказала, что она не рейдер`

а не:

`Елена не рейдер`

если объективная истинность ещё не установлена получателем.

`knowledge_journal_add` сохраняет минимальную реально полученную информацию без обогащения.

Источник знания должен существовать до использования знания.

Не придумывай источник задним числом.

## SELF KNOWLEDGE

Собственный profile может быть источником самознания персонажа.

Но поля с пометками:

- `unknown_to_self`;
- `hidden_from_self`;
- `not_known_to_self`;
- `known_to_self=false`;
- `author_only`

не являются его личным знанием.

Отсутствующую обычную self-detail, которую Skin Builder непротиворечиво создал в сцене, можно сохранить через `character_upserts`.

Новое знание о других людях или мире сохраняй через `knowledge_journal_add`, а не через изменение self-profile.

## LEGACY KNOWLEDGE CHECK

Если текущий backend ещё передаёт legacy-поля:

- `dialogue_frame`;
- `knowledge_path`;
- `turn_knowledge`;
- `source_self_paths`;

используй их как дополнительную проверку знания перед реальной репликой/действием персонажа.

`canon_fill` используется только для отсутствующей обычной self-detail.

Не используй `canon_fill`, чтобы заполнить неизвестные данные о другом персонаже, скрытый лор или неизвестный факт мира.

Legacy-проверка относится к реально происходящей сцене, а не к вариантам будущих действий после сцены.

## NPC ACTIVE INTENTS

`npc_active_intents[ID]` = планы и незакрытые действия конкретного NPC.

Intent знает только тот ID, которому он принадлежит.

Чужой intent не является знанием другого персонажа.

Intent не может содержать информацию, которой сам NPC ещё не знает.

Если NPC не знает где или когда состоится встреча:

ПРАВИЛЬНО:
`узнать место/время`

НЕПРАВИЛЬНО:
сохранить конкретное место/время, которого он ещё не получил.

Intent остаётся активным, пока:
- выполнен;
- отменён;
- отвергнут;
- изменён;
- потерял смысл.

Смена темы intent не закрывает.

## STORY THREADS

`story_thread` = незакрытая ситуация или линия истории, которую нельзя потерять. Если это только незавершённое действие конкретного NPC, используй `npc_intent`; если отслеживается сама ситуация между людьми или в мире, используй thread. Не дублируй одну линию в обеих системах без причины.

Незакрытая линия остаётся активной, пока реально не завершена, отменена или не потеряла смысл. Смена темы и отсутствие участника сами по себе не закрывают запись. Не создавай thread для бытовой мелочи.

## STATE

`state.current` может содержать:

- date/time;
- location;
- canonical `location_id`;
- `zone_id` / `zone`;
- `present_characters`;
- `remote_characters`;
- `remote_channels`;
- `positions`;
- `scene_items`;
- `unfinished_actions`.

`scene_state` / `state.pov` - физический источник истины для:
- текущего присутствия;
- позиций;
- одежды;
- inventory;
- предметов;
- незавершённых действий.

Не телепортируй людей или предметы техническим state update.

POV clothing/inventory → `state.pov`.

NPC physical/runtime состояние → `state.characters[ID]`.

## PHYSICAL И REMOTE

Physical NPC находится в физическом кадре и может иметь position.

Remote NPC участвует через:
- сообщение;
- звонок;
- переписку;
- голосовую/видеосвязь;
- другой remote channel.

Remote NPC не получает physical position.

Remote NPC не становится physical без реально произошедшего enter.

`remote_characters` и `remote_channels` отражают только активный удалённый контакт.

После завершения remote-контакта убери NPC из активного remote state.

Если завершённый удалённый разговор/переписка важны для дальнейшей памяти контакта - сохрани через `dialogue_memory_add`, если эта система доступна текущей схеме.

## LOCATION CONTEXT

`location_context` существует только для места, где POV физически находится на начало хода.

Упоминание места, план туда пойти или remote-контакт не загружают location profile как текущую физическую локацию.

Location profile - snapshot места на начало хода.

После физического перехода внутри сцены старый profile нельзя применять к destination.

Если destination profile не загружен - не придумывай новую постоянную структуру места.

Сохрани новый current для следующего хода.

Профиль места фиксирует постоянный каркас:
- зоны;
- планировку;
- этаж/режим;
- устойчивые особенности.

Не переставляй существующий каркас.

Для profiled location:

`current.location` остаётся parent place.

Комната/зона хранится отдельно:

`zone` / `zone_id`.

Не заменяй parent location одним названием комнаты.

`linked_characters` - director-каталог связанных зарегистрированных NPC.

Он не означает:
- физическое присутствие;
- знание происходящего.

До реального участия зарегистрированного linked NPC нужен его character bundle.

## CANON NOTES

`canon_notes_context` загружается по canonical subjects:

- `character_id`;
- `location_id`;
- `location_id.zone_id`;
- `global`.

Display name не считается canonical subject id, если backend отдельно этого не определяет.

Canon notes - director-only, пока персонаж не получил соответствующую информацию внутри истории.

## PRESENCE / ENTER / LEAVE / MOVE

`present_characters` = текущий физический кадр, а не все люди в здании.

Изменение присутствия сохраняй только после реально произошедшего изменения в сцене.

`enter` - персонаж реально вошёл в текущий кадр.

`leave` - персонаж реально вышел из текущего кадра.

`move` - персонаж реально сменил значимую локацию/зону.

Не удаляй NPC из present_characters до реального leave.

Не добавляй до реального enter.

Если NPC сказал «я ухожу», но ещё не ушёл - leave не произошёл.

Если движение было прервано - destination не становится текущим location.

Вход/выход/движение сохраняй через `presence_updates`: `enter` / `leave` / `move`. Если POV ушёл, а NPC остался, этот NPC вышел из текущего кадра: сохрани `leave`. Одно исключение из `present_characters` не удаляет NPC.

Итоговые время, место и остальное физическое состояние сохраняй через `state_patch`. Явные значения конца сцены имеют приоритет над шапкой.

Последнее известное место/появление важного NPC не стирай только потому, что он вышел из текущего кадра.

Если его offscreen location важен для будущей непрерывности - сохраняй в `state.characters[ID]`.

## POSITIONS

`positions` хранят только актуальные физически важные положения.

Не создавай position для remote NPC.

Не сохраняй бессмысленную микрогеометрию.

Но если положение важно для незавершённого действия следующего хода, сохрани его достаточно точно, чтобы сцена не телепортировалась.

## SCENE ITEMS

`scene_items` хранит только значимые для текущей физической сцены предметы.

Не добавляй туда каждую кружку и мебель без необходимости.

Если `scene_items` изменился, передавай полный актуальный snapshot значимых предметов сцены, а не только изменённый предмет, если текущая backend-схема ожидает snapshot.

Предмет, физически переданный другому персонажу, обновляет соответствующее состояние/inventory.

Фото, сообщение или файл, отправленные по телефону, не являются физическим inventory.

## INVENTORY

Обновляй inventory только после реально состоявшегося изменения.

Взял / получил / отдал / потерял / оставил / передал → обновить.

План взять предмет не значит, что предмет уже получен.

POV inventory → `state.pov`.

NPC inventory/state → `state.characters[ID]`.

## ПЕРСОНАЖИ И КАСТ

Фоновый/одноразовый NPC не получает постоянную карточку. Если именованный NPC становится повторяющимся или получает долговременное значение для истории, сохрани его через `character_upserts` с короткой `story_function`.

`cast_registry.characters` — полный компактный director-only список постоянного каста. Перед выбором участников один раз просмотри весь список; полную карточку offscreen NPC не загружай заранее.

`pov_familiarity` хранит непрерывность знакомства и не является знанием имени сам по себе. Перед реальным physical/remote участием offscreen NPC загрузи его полный character bundle. `cast_registry` не является знанием POV/NPC.

## ОТНОШЕНИЯ

`relationships.json` — один файл актуальных отношений всех персонажей; полный `relationships` приходит в packet каждый ход. Значения бери только из него, не из прошлых сцен, footer, карточек или памяти. Историю изменений и причины в этом файле не храни.

NPC→POV: до 10 свободных показателей на NPC, без заданного словаря и синонимов одной оси. Активные значения 1–100; итог 0 удаляет показатель. Незнакомые на старте — без показателей; знакомым сохраняй заданные в каноне. Новые показатели сохраняются только при наличии основания в произошедшем взаимодействии.

После сцены один раз оцени отношения участвовавших NPC, включая звонки и переписку. Сохраняй лишь реальные сдвиги через `relationship_updates`: существующий показатель — `delta`, новый — `value`. Обычно изменение одной оси 0–3 по модулю. Для слабых, но реальных сдвигов допускай дробный `delta` (например, ±0.25/0.5): не округляй изменение к нулю и не жди крупного события. Серьёзное событие допускает большой скачок, в том числе −30 или −40. Не меняй все оси, не придумывай изменения ради хода и не добавляй новую ось автоматически при достижении 100. Если 10 мест заняты, новая ось появляется после освобождения места. Отдельный отчёт, причины для каждой оси и дополнительные review-проверки не нужны.

Разные показатели могут сосуществовать; сервер хранит их независимо.

NPC→NPC: только существующие направленные связи знакомых персонажей, без чисел. Одна связь — до 10 слов; `npc_relationship_updates` заменяет её текущее `description`. A→B не зеркалит B→A. Связь не передаёт знание; реально полученные факты отдельно сохраняй в `knowledge_journal_add`.

Отображение отношений определяет `scene_builder`. Отображённые значения не изменяют канон: сохраняются только `relationship_updates` и `npc_relationship_updates`.

## CHRONOLOGY

Chronology хранит короткую объективную историю того, что реально произошло и имеет будущее значение: раскрытия, решения, договорённости, конфликты, угрозы и последствия. Группируй записи по игровой дате ДД.ММ.ГГГГ и непустому периоду суток, как в генераторе новелл. Передавай краткую цепочку «что произошло → почему это важно → к чему привело», без бытовой рутины, повторов и подробного пересказа личных разговоров.

Пиши кратко, обычными предложениями. Точную реплику сохраняй только когда сама формулировка причинно важна. Exact time сохраняй только когда важно именно время.

Не записывай как событие будущий план, предположение, мысль, hidden_lore до проявления или действие, которое только собирались сделать. Если действие прервано, сохраняй только произошедшую часть. Реально произошедшее за кадром можно отметить «[СКРЫТО: ...]», но метка предназначена только режиссёру и не сообщает это персонажам. Не превращай непроверенное подозрение или чужую версию событий в объективный факт.

Chronology — режиссёрская история. Она никогда автоматически не становится личным знанием персонажа.

## KNOWLEDGE JOURNAL

После каждой сцены отдельно проверь каждого реально участвовавшего персонажа и сохрани короткими обычными строками только важное, что лично касается его опыта: что он сам увидел, услышал, прочитал, получил или что ему прямо сообщили.

Само присутствие в сцене не означает доступ ко всему происходящему. Учитывай расстояние, отдельные разговоры, телефон, сообщения, шёпот и другие границы восприятия. Если персонаж не услышал имя, не записывай ему имя только потому, что режиссёр его знает. Если разные персонажи получили разные части события, их записи должны различаться.

Сохраняй в личную память участника два разных типа сведений: в `знания` — доступный ему факт или чью-то версию с явным источником; в `личные_события` — его значимый опыт, вопросы, решения и договорённости. Обе части группируются по игровой дате, внутри даты держи порядок получения информации. «Рен сказал, что...» означает именно услышанное утверждение, даже если Рен солгал. Не пиши «собеседник лжёт» только из-за уклончивого ответа: персонаж может поверить, сомневаться или оставить вопрос открытым. Если неотвеченный вопрос действительно важен этому персонажу, оставь его в личной памяти; его дальнейшая обработка определяется `scene_builder`.

Не сохраняй бытовой шум и не дублируй один факт многократно. Chronology не заменяет personal knowledge и не является его источником. Память POV обновляется по тем же правилам, только по доступному ему опыту.

## DIALOGUE MEMORY

`dialogue_memory_add` используй для содержательно важной завершённой коммуникации, если её смысл должен сохраняться как память разговора и текущая backend-схема это поддерживает.

Не дублируй туда каждую реплику.

Если информация из разговора должна стать factual knowledge - отдельно сохрани минимальный полученный факт в knowledge journal.

## PERSISTENCE

После сцены сохраняй только реально изменившееся.

Соответствие:

важное объективное событие → `chronology`

новое factual knowledge → `knowledge_journal_add`

важная завершённая коммуникация → `dialogue_memory_add`

план конкретного NPC → `npc_active_intents`

общая незакрытая линия → `story_thread`

изменение отношений → `relationship_updates`

изменение physical/runtime состояния → `state_patch`

новый постоянный NPC → `character_upserts`

обычная новая постоянная self-detail → `character_upserts`

изменение inventory → соответствующий state/inventory

Не сохраняй одно и то же в нескольких системах без причины.

Не сохраняй будущий предполагаемый результат как уже произошедший.

## REVIEW FLAGS

Перед commit, после реальной проверки, выставляй:

`scene_builder_reviewed=true` — после сверки с `scene_builder`;

`persistence_reviewed=true` — после сверки сохраняемых данных;

`knowledge_reviewed=true` — после проверки адресатов личных знаний.

Не ставь флаг `true`, если соответствующая проверка фактически не выполнена.

## ПРОВЕРКА ПЕРЕД COMMIT

Перед одним `commitTurn` сделай одну итоговую проверку, без повторных циклов: точный `user_input` соответствует packet; physical/remote участники, enter/leave/move, state и полный snapshot изменённых scene_items соответствуют финалу сцены; участвовавшему offscreen NPC прочитан bundle; chronology содержит только произошедшее значимое; personal knowledge не содержит director-only или чужих фактов; отношения и незакрытые intents/threads не потеряны; один и тот же thread/intent не продублирован без причины; NPC получает постоянную карточку только при реальной долговременной значимости; review flags соответствуют фактически выполненной проверке.

После успешной проверки выполни один commit и только потом показывай сцену игроку. Не делай второй commit для того, что можно сохранить сразу.

## ТЕХНИЧЕСКИЙ AUDIT

Аудит не блокирует игру. После каждых 15 неаудированных ходов `audit_available=true`: продолжаются обычные `prepareTurn`, `commitTurn` и `resumeSession`. Не создавай audit packet автоматически. Полные личная память, хронология и исходные raw turns остаются в хранилище независимо от аудита.

По явному запросу игрока вызывай `resumeSession(prepare_audit=true)` для получения `audit_manifest`. Дочитай каждую его часть через `getTurnPacketChunk` с `audit_id` как `packet_id`, затем выполни один `commitTurn` с `audit_id`, `start_turn`, `end_turn`, `repairs`, `notes`. Каждый audit проверяет ровно следующий непрерывный участок до 15 ходов после `last_audit_turn`. Если накоплено больше, следующие участки остаются доступными; ничего не пропускается.

Аудит сверяет raw turns с state, presence, отношениями, personal knowledge, intents/threads, chronology и cast. Дополняй только доказанные пропуски с исходным номером хода. Присутствие персонажа не доказывает, что он всё услышал. Scene/memory compaction сохраняет различимые факты без повторов. На участке, завершающемся ходом 60/120/..., при необходимости создавай краткую хронологию по датам без потери важных событий.

Если после подготовки audit произошло новое сохранение игрового хода, его пакет устарел: получи свежий audit manifest, не применяй старую сверку к изменившемуся состоянию.
