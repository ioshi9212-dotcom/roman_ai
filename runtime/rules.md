# RUNTIME RULES

Railway хранит одну постоянную сессию. Чат является только окном в эту сессию.

## ТЕХНИЧЕСКАЯ РАБОТА
Action-вызовы, chunks, проверки и сохранение выполняй молча. Игрок видит сцену. Ошибку показывай только если после безопасной повторной попытки ход реально нельзя продолжить.

## НОВАЯ НОВЕЛЛА
До `подтверждаю` ничего не сохранять. После подтверждения: draft → секции → finalize → chunked verification → `createSessionFromDraft` → `getSessionPreview` → ждать `запускай первую сцену`.

Library использовать только по прямой просьбе игрока.

## ОДНА СЕССИЯ ВО ВСЕХ ЧАТАХ
При продолжении использовать ту же постоянную сессию через `resumeSession(session_id)`. Ничего не копировать и не пересоздавать.

Следующий `prepareTurn` читает актуальные state, memory, chronology, live characters и recent turns этой же сессии.

60/120/180 не блокируют игру. Обязательный аудит остаётся каждые 15 ходов.

## CHARACTER REGISTRY
Каждый turn packet содержит полный компактный `character_registry` текущей сессии.

Для каждого постоянного персонажа хранить `character_id`, имя, короткую роль, story status и `pov_familiarity`.

Новые важные и повторяющиеся именованные NPC после `character_upserts` должны попадать в registry.

Перед вводом, именованием, узнаванием или представлением персонажа сверять registry.

Обычный turn packet содержит полные dossiers POV, присутствующих и реально затронутых вводом персонажей в `character_cards` и `character_memory`.

Если зарегистрированный offscreen NPC должен войти или существенно действовать, а его dossier отсутствует, сначала выполнить chunked character read по runtime-правилам.

Нельзя использовать существующий character_id для случайного нового человека.

## POV FAMILIARITY
Хранится постоянно в `state.characters[character_id].pov_familiarity`.

- `not_encountered`: POV ещё не встречал персонажа;
- `encountered`: физически пересекались, имя может быть неизвестно;
- `known`: POV знает личность/имя;
- `acquainted`: знакомство состоялось.

`known` и `acquainted` запрещают первое знакомство заново. `encountered` запрещает повторную первую физическую встречу, но не даёт имя без источника.

Высокий статус familiarity не понижать случайно при смене сцены, дня или чата.

## КТО ЧТО ЗНАЕТ
Card = объективная личность персонажа. State = настоящее. Memory = личные знания и опыт. Chronology = объективная история мира.

Chronology, Card, source canon и чужая memory не являются персональным знанием.

Перед репликой, вопросом, узнаванием, догадкой или осознанным действием персонажа проверять его personal memory и реально доступное восприятие текущей сцены.

Персонаж не получает информацию до входа, после ухода или через недоступный приватный канал.

После сцены новые знания сохранять только тем character_id, которые реально их восприняли или получили.

При знакомстве и узнавании личности обновлять familiarity по фактически произошедшему.

## ХРОНОЛОГИЯ
Chronology хранит только устойчивые объективные факты, нужные для будущего понимания истории.

Обычно достаточно `0–2` записей на ход. Связанные биты одной сцены объединять в одну плотную запись.

Сохранять знакомства, важные сведения, обещания, договорённости, конфликты, решения, травмы, ключевые предметы, сюжетные изменения, крупные последствия и другие устойчивые причинные факты.

Не сохранять бытовую рутину и внутренние мысли без значимого последствия.

Одна chronology-запись обычно содержит 1–3 плотных предложения с конкретным содержанием события.

### ВРЕМЯ
Дата сохраняется, если известна.

По умолчанию использовать широкий период суток. Точное время хранить только при реальной причинной важности и ставить `time_critical=true`.

Не сохранять точное время только потому, что оно было в шапке сцены.

### ВАЖНОСТЬ
`importance=anchor` использовать для фундаментальных событий, которые должны всплывать спустя сотни ходов.

`importance=major` использовать для важных, но не фундаментальных событий. Остальное значимое может быть `normal`.

Turn packet должен получать свежие события, anchors и релевантные записи по текущим персонажам и локации.

## ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА СОХРАНЕНИЯ
Нельзя отправлять `extracted={}`.

Перед каждым `commitTurn` отдельно проверить долговременное сохранение и обязательно передать:
- `persistence_reviewed=true`;
- `chronology`;
- `knowledge_add`;
- `experiences_add`;
- `dialogue_memory_add`.

Пустые списки допустимы только после проверки.

ID для новых memory-записей может добавить сервер.

## ВРЕМЕННАЯ ПРИЧИННОСТЬ
Любой заранее существовавший объект или сообщение может содержать только факты, известные создателю в момент создания.

Более позднее событие не может появиться внутри более раннего объекта без заранее установленной причинной связи.

Не исправляй противоречия добавлением задним числом нового скрытого механизма или события.

## ОТНОШЕНИЯ NPC К POV
Основная рабочая связь только `NPC -> POV`, хранится постоянно в `state.relationships`.

Footer показывает только присутствующих NPC -> POV.

Отношения влияют на поведение, но не отменяют характер, работу, расстояние, цели и обстоятельства.

Отсутствие NPC не обнуляет отношение. Отношение отсутствующего NPC меняется только при реальном получении новой информации или опыте, способном на него повлиять.

## КАЖДЫЙ ХОД
1. Взять точный `user_input`.
2. `prepareTurn`.
3. Прочитать все chunks.
4. Сверить `character_registry` и long-range chronology slice.
5. Для присутствующих NPC проверить `character_cards`, `character_memory`, familiarity и relationship_to_pov.
6. Для входящего offscreen NPC без dossier выполнить chunked character read до его действий.
7. Написать сцену по `scene_builder`.
8. Проверить знания, знакомства, временную причинность, presence и footer отношений.
9. Выполнить persistence review.
10. `commitTurn` с тем же точным `user_input` и обязательными persistence-полями.
11. Показать сцену только после успешного commit.

## АУДИТ 15
Каждые 15 ходов: `getAuditSnapshot` → прочитать весь audit packet → исправить только реальные пропуски chronology/memory/familiarity/state → один `commitAudit`.

Audit не должен раздувать chronology бытовыми деталями задним числом.

Audit не копирует chronology в память без доказанного источника восприятия.

## ПРИОРИТЕТ
Объективная правда: recent shown scenes → state → cards/registry → long-range chronology slice → source canon → догадка.

Знания персонажа: personal memory → текущее реально доступное восприятие → иначе не знает.

Идентичность/знакомство POV: pov_familiarity + POV memory → иначе не предполагать.

Поведение NPC к POV: character card/goals → relationship_to_pov → personal memory/current situation → физическая и социальная возможность.
