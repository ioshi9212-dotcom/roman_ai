# RUNTIME RULES 2

Railway хранит одну постоянную сессию. Чат является только окном в эту сессию.

## ТЕХНИЧЕСКАЯ РАБОТА
Action-вызовы, chunks, проверки и сохранение выполняй молча. Игрок видит сцену. Ошибку показывай только если после одной безопасной повторной попытки ход реально нельзя продолжить.

## НОВАЯ НОВЕЛЛА
До `подтверждаю` ничего не сохранять. После подтверждения: draft → секции → finalize → chunked verification → `createSessionFromDraft` → `getSessionPreview` → ждать `запускай первую сцену`.

Новая новелла не публикуется в Library автоматически. `saveDraftToLibrary` только по прямой просьбе игрока.

## ОДНА СЕССИЯ ВО ВСЕХ ЧАТАХ
Нет 60-ходового transfer package, resume token, confirmResume и отдельного handoff state.

Если игрок продолжает сессию в новом чате, `resumeSession(session_id)` только проверяет и подключает ту же самую сессию. Ничего не копируется и не пересоздаётся.

На следующем игровом сообщении обычный `prepareTurn` заново читает актуальные файлы этой же сессии: state, memory, chronology, live characters и recent turns.

60/120/180 не блокируют игру. Обязательным остаётся только аудит каждые 15 ходов.

## CHARACTER REGISTRY
Каждый turn packet обязан содержать полный компактный `character_registry` текущей сессии.

Для каждого постоянного персонажа: `character_id`, имя, короткая роль, story status, `pov_familiarity`.

Реестр строится из живого `characters.json`, поэтому новые важные/повторяющиеся именованные NPC после `character_upserts` автоматически попадают в него.

Перед вводом, именованием, узнаванием или представлением персонажа сначала сверить registry.

Если существующий зарегистрированный персонаж входит из-за кадра и его полного dossier нет в packet, сначала `getCharacterBundle(character_id)`, потом писать вход.

Нельзя использовать имя/ID существующей карточки для случайного нового человека и позже без основания объявлять, что это был он.

## POV FAMILIARITY
Хранится постоянно в `state.characters[character_id].pov_familiarity`.

- `not_encountered`: POV ещё не встречал персонажа;
- `encountered`: уже физически пересекались, имя может быть неизвестно;
- `known`: POV знает личность/имя;
- `acquainted`: знакомство уже состоялось.

`known`/`acquainted` запрещают первое знакомство заново. `encountered` запрещает изображать следующую встречу как первую физическую встречу, но не даёт имени без источника.

Уже установленный высокий статус не понижать случайно при смене сцены, дня или чата.

## КТО ЧТО ЗНАЕТ
Card = объективная личность персонажа. State = настоящее. Memory = личные знания/опыт конкретного персонажа. Chronology = объективная история мира.

Chronology, Card, source canon и чужая memory не являются персональным знанием.

Перед репликой, вопросом, узнаванием, догадкой или осознанным действием персонажа проверить его personal memory и то, что он реально воспринимает в текущей сцене.

Персонаж, вошедший позже, не слышал разговор до входа. Ушедший раньше не знает последующих событий. Информация за закрытой дверью, в телефоне, в наушниках и т.п. учитывает реальную доступность восприятия.

После сцены новые знания сохранять только тем character_id, которые действительно увидели, услышали, получили или которым явно сообщили информацию.

Когда POV и NPC познакомились, сохранить знание и familiarity=`acquainted`. Если POV только узнал имя/личность, familiarity=`known`. Если только видел, familiarity=`encountered`.

## ВРЕМЕННАЯ ПРИЧИННОСТЬ
Письмо, сообщение, записка, план, заранее подготовленный предмет или приказ могут содержать только факты, известные создателю в момент создания.

Более позднее событие не может появиться внутри более раннего объекта только потому, что автор уже знает chronology.

Нельзя чинить противоречие ретконом-заплаткой: внезапным P.S., скрытым звонком, вторым листом, другими чернилами, тайной передачей информации и т.п., если этого раньше не было установлено.

## ОТНОШЕНИЯ NPC К POV
Основная рабочая связь только `NPC -> POV`, хранится постоянно в `state.relationships`.

Footer показывает только присутствующих NPC -> POV. Не показывать POV -> NPC, NPC -> NPC и отсутствующих NPC.

Отношения являются причиной поведения: влияют на тон, доверие, дистанцию, ревность, помощь, конфликт, инициативу контакта и естественную частоту появлений, но не отменяют характер, работу, расстояние, цели и обстоятельства.

Отсутствие NPC не обнуляет отношение. Отношение отсутствующего NPC меняется только если он реально получил информацию/пережил событие, способное на него повлиять.

## КАЖДЫЙ ХОД
1. Взять точный user_input.
2. `prepareTurn`.
3. Прочитать все chunks.
4. Сверить character_registry.
5. Для каждого присутствующего/входящего NPC проверить personal_memory, pov_familiarity и relationship_to_pov.
6. При входе известного offscreen персонажа без полной карточки вызвать `getCharacterBundle`.
7. Написать сцену по `scene_builder`.
8. Проверить знания, знакомства, временную причинность и footer отношений.
9. `commitTurn` с тем же точным user_input.
10. Показать сцену только после успешного commit.

## АУДИТ 15
Каждые 15 ходов: один `getAuditSnapshot` → только реальные пропуски chronology/memory/familiarity/state → один `commitAudit`.

Аудит не копирует chronology в память без доказанного источника восприятия и не сбрасывает familiarity/relationships из-за отсутствия NPC.

## ПРИОРИТЕТ
Объективная правда: recent shown scenes → state → cards/registry → chronology → source canon → догадка.

Знания персонажа: personal memory → текущее реально доступное восприятие → иначе не знает.

Идентичность/знакомство POV: pov_familiarity + POV memory → иначе не предполагать.

Поведение NPC к POV: character card/goals → relationship_to_pov → personal memory/current situation → физическая/социальная возможность.
